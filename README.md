## 1. 项目简介

### 1.1 项目概述

本项目是一个基于 RAG（Retrieval-Augmented Generation，检索增强生成）技术构建的**电商运营智能助手**。系统通过对电商运营相关文档（淘宝/天猫/抖音电商运营指南）进行知识抽取、向量化存储和智能检索，结合大语言模型的生成能力，为电商运营人员提供专业、准确的问答服务。

### 1.2 核心功能

- **智能问答**：基于知识库内容，回答电商运营相关问题
- **多格式文档支持**：支持 PDF（含扫描版）、DOCX、PPTX、XLSX、CSV、TXT、Markdown 等多种格式
- **多模态检索**：同时支持文本语义检索和图片检索（基于 CLIP）
- **混合检索策略**：语义检索 + BM25 关键词检索 + RRF 融合 + 神经网络重排序
- **对话记忆**：短期记忆（会话摘要）+ 长期记忆（用户兴趣画像）
- **流式响应**：基于 SSE 的实时流式回答
- **知识库管理**：独立的管理后台，支持文档上传、查看、管理
- **用户系统**：独立的用户认证体系（管理员 + 普通用户）
- **自动化评估**：基于 RAGAS 的 RAG 质量评估系统

### 1.3 应用场景

- 电商新人快速学习店铺运营知识
- 运营人员查询具体操作流程和最佳实践
- 团队知识沉淀与共享

## 4. RAG 技术原理

### 4.1 什么是 RAG

RAG（Retrieval-Augmented Generation）是一种将信息检索与文本生成相结合的技术架构。它通过在大语言模型生成答案之前，先从外部知识库中检索相关文档片段作为上下文，从而让模型能够基于最新、准确的领域知识生成回答。

**RAG 解决的核心问题：**
- **知识时效性**：LLM 训练数据有截止日期，RAG 可引入最新知识
- **幻觉问题**：LLM 可能生成看似正确但实际错误的内容，RAG 提供事实依据
- **领域专业性**：通用 LLM 对垂直领域知识覆盖不足，RAG 补充专业知识
- **可解释性**：RAG 能追溯答案来源，提高可信度

### 4.2 RAG 工作流程

```
用户提问 ──→ 查询改写 ──→ 混合检索 ──→ 结果融合 ──→ 重排序 ──→ 上下文构建 ──→ LLM生成 ──→ 流式输出
                │              │            │           │            │              │
                ▼              ▼            ▼           ▼            ▼              ▼
           消除指代      语义 + BM25     RRF算法    CrossEncoder   注入记忆       Qwen模型
           补充上下文    双路召回        排名融合    精细打分      + 图片检索     流式生成
```

### 4.3 核心技术组件

#### 4.3.1 文档处理与分块（Chunking）

分块是 RAG 系统的基础环节，直接影响检索质量。本项目采用**多策略分块**方案：

| 文档类型 | 分块策略 | 原理 |
|----------|----------|------|
| Markdown/DOCX | 标题层级分割 | 按 `#`、`##`、`###` 标题自然分割，保留文档结构 |
| PDF | 语义分块 | 先粗切（2000字符），再用 SemanticChunker 按语义相似度细分 |
| PPTX | 幻灯片分割 | 按幻灯片页边界自然分割 |
| XLSX | 工作表分割 | 按 Sheet 边界分割 |
| 通用 | 递归字符分割 | 作为兜底策略，超长块（>2000字符）强制切分 |

**SemanticChunker 原理**：通过计算相邻句子的 Embedding 相似度，在语义断裂点（相似度低于阈值处）切分文本，确保每个块内语义连贯。本项目使用百分位阈值法（90th percentile），即在相似度降幅最大的 10% 位置切分。

#### 4.3.2 向量嵌入（Embedding）

将文本转化为高维向量空间中的稠密向量表示，使得语义相似的文本在向量空间中距离更近。

- **文本嵌入**：阿里 DashScope `text-embedding-v4` 模型，支持中文语义理解
- **图片嵌入**：CLIP（`clip-ViT-B-32`）模型，将图片和文本映射到同一向量空间

#### 4.3.3 混合检索（Hybrid Retrieval）

单一检索方式各有局限，本项目结合两种互补的检索策略：

**语义检索（Dense Retrieval）**：
- 基于向量余弦相似度
- 优势：理解同义词、语义相近的表述
- 劣势：对精确关键词匹配能力较弱

**BM25 关键词检索（Sparse Retrieval）**：
- 基于词频-逆文档频率（TF-IDF 变体）
- 使用 jieba 进行中文分词
- 优势：精确匹配关键词、专有名词
- 劣势：无法理解语义相似性

#### 4.3.4 RRF 融合（Reciprocal Rank Fusion）

将两路检索结果合并为统一排名：

```
RRF_score(d) = Σ 1 / (k + rank_i(d))
```

其中 `k` 为平滑常数（本项目取 60），`rank_i(d)` 为文档 d 在第 i 个检索列表中的排名。RRF 的优势在于不依赖绝对分数，只依赖排名顺序，因此对不同量纲的分数体系具有良好的兼容性。

#### 4.3.5 重排序（Reranking）

使用 BGE-Reranker-v2-M3 交叉编码器对 RRF 融合后的候选文档进行精细化打分：

- 交叉编码器将 query 和 document 拼接后联合编码，能捕捉更精细的交互特征
- 相比双塔模型（Bi-Encoder），精度更高但速度较慢
- 本项目先用双塔模型粗筛（top-6 × 2 = 12 候选），再用交叉编码器精排（取 top-3）

#### 4.3.6 查询改写（Query Rewriting）

用户在对话中经常使用代词或省略主语，如：
- "它的价格是多少？"（"它"指代上文提到的产品）
- "还有呢？"（省略了具体询问对象）

查询改写模块通过 LLM 将这类模糊查询结合上下文改写为完整、独立的查询语句，提高检索准确率。

#### 4.3.7 记忆系统（Memory）

```
┌─────────────────────────────────────┐
│            记忆系统                   │
├─────────────────┬───────────────────┤
│    短期记忆      │     长期记忆       │
│ (会话摘要)       │  (用户兴趣画像)    │
├─────────────────┼───────────────────┤
│ 保留最近6条消息  │ 20个电商主题分类   │
│ 更早消息压缩为   │ 记录用户关注的     │
│ 摘要注入上下文   │ Top-5兴趣领域     │
└─────────────────┴───────────────────┘
```

**短期记忆**：滑动窗口保留最近 6 条对话，超出部分由 LLM 压缩为摘要，避免上下文过长但保留关键信息。

**长期记忆**：基于 LLM 对每轮对话进行主题分类（20 个电商领域类别），累计统计用户关注的 Top-5 领域，用于个性化回答。

## 5. 系统实现流程

系统采用经典的 RAG 架构，分为**知识库更新**和**在线检索生成**两个核心部分。

### 5.1 知识库更新流程

知识库更新部分负责将原始文档（电子书、PDF 报告等）转化为可供检索的向量化知识。整个流水线由 `KnowledgeBaseService` 服务统一编排，实现了从文档上传到向量入库的全流程自动化。

#### 5.1.1 数据预处理

在知识库更新服务中，管理员通过前端界面将文件上传至 Flask 服务端。服务端根据文件扩展名自动识别文档格式，进入对应的解析分支。每种格式有专门的解析逻辑，并封装在 `read_file_content()` 函数中。

**表 4：知识库更新服务中的文档解析方式**

| 文档格式 | 解析工具 | 处理方式 | 特殊处理 |
|----------|----------|----------|----------|
| **PDF（文字版）** | PyMuPDF (fitz) | 逐页提取文本内容 | TableTransformer 检测表格 + PaddleOCR 识别单元格内容 |
| **PDF（扫描版）** | PaddleOCR | 检测为扫描版后，将页面渲染为 150 DPI 图片，多线程并行 OCR | 通过 CJK 字符占比 < 5% 或可打印字符 < 80% 判定为扫描版 |
| **DOCX** | python-docx | 提取段落文本和表格 | 保留标题层级，转换为 Markdown 格式（# ## ###） |
| **PPTX** | python-pptx | 逐页提取文本框和表格内容 | 以 `[幻灯片 N]` 标记每页边界 |
| **XLSX** | openpyxl | 读取所有工作表 | 转换为 Markdown 表格格式，以 `[Sheet: ...]` 分隔 |
| **CSV** | csv 模块 | 标准 CSV 解析 | 转为制表符分隔的文本 |
| **TXT** | 直接读取 | UTF-8 编码读取 | 无需特殊处理 |
| **Markdown** | 直接读取 | UTF-8 编码读取 | 剔除 HTML 标签 |

**扫描版 PDF 处理细节**：
- **自动检测**：通过启发式规则判断（CJK 字符占比 < 5% 或可打印字符占比 < 80%）
- **页面渲染**：使用 PyMuPDF 将每页渲染为 150 DPI 的图片
- **并行 OCR**：创建 4 个工作线程并行处理，显著提升速度
- **文本合并**：按页码顺序合并 OCR 结果

#### 5.1.2 数据清洗策略

清洗后的文本需要去除无效内容，保留有价值的知识片段。本系统实现的 `clean_text()` 函数包含以下清洗规则：

**清洗规则详解**：

1. **页码移除**：
   - 匹配独立数字行（如 "- 42 -"、"第 42 页"）
   - 使用正则表达式识别常见页码格式

2. **页眉页脚移除**：
   - 检测重复出现的短行模式
   - 移除章节标题、日期等重复性内容

3. **目录检测与移除**：
   - 采用滑动窗口（10 行）检测
   - 若 3+ 行匹配 "标题...页码" 模式且连续 5+ 行命中，则移除整块
   - 有效避免目录页干扰语义检索

4. **版权页检测**：
   - 识别包含 ISBN、版权、出版社等关键词的段落
   - 移除版权声明及前后 2 行

5. **PDF 断行合并**：
   - 检测非句末标点（。！？；…）结尾的行
   - 与下一行合并，恢复完整语义

6. **空白归一化**：
   - 连续空行压缩为单行
   - 行内多空格压缩为单个空格

7. **短碎片过滤**：
   - 过滤长度 < 5 字符的行
   - 减少噪声干扰

#### 5.1.3 数据切分策略

清洗后的文本需要划分为适合向量检索的语义块（chunk）。本系统采用**"格式感知"的自适应分块策略**，即根据文档格式选择最优切分方法。

**表 5：各类文档的数据切分策略**

| 文档类型 | 分块策略 | 技术实现 | 优势 |
|----------|----------|----------|------|
| **Markdown / DOCX** | 标题层级分割 | `MarkdownHeaderTextSplitter` 按 `#`、`##`、`###` 分割 | 保留文档结构，语义完整性强 |
| **PDF** | 递归字符切割 | RecursiveCharacterTextSplitter（600 字符，100 重叠）切分 | 兼顾速度与质量 |
| **PPTX** | 幻灯片边界分割 | 按 `[幻灯片 N]` 标记分割 | 每页内容自然成块 |
| **XLSX** | 工作表边界分割 | 按 `[Sheet: ...]` 标记分割 | 保持表格数据完整性 |
| **TXT / 其他** | 语义分块 | 直接使用 `SemanticChunker` | 自动识别语义边界 |
| **通用兜底** | 递归字符分割 | 对超长块（> 2000 字符）强制切分 | 防止块过大影响检索 |

**SemanticChunker 工作原理**：
1. 将文本分割为句子
2. 计算相邻句子的 Embedding 余弦相似度
3. 在相似度骤降处（低于百分位阈值）进行切分
4. 本项目使用 90th percentile，即在相似度降幅最大的 10% 位置切分

#### 5.1.4 文本向量化

分块完成后，每个文本 chunk 通过阿里云的 `text-embedding-v4` 模型转换为 **1024 维**的高维嵌入向量，再批量写入 ChromaDB。

**向量化流程四阶段**：

1. **向量嵌入**：
   - 调用 `DashScopeEmbeddings`，使用 `text-embedding-v4` 模型
   - 支持批量处理，提高效率

2. **元数据附加**：
   - `source`：源文件名
   - `create_time`：入库时间戳
   - `operator`：操作者（管理员账号）
   - `page_nums`：原始页码（用于溯源）

3. **入库容错**：
   - 若批量写入失败，逐条重试
   - 跳过损坏的 chunk，确保合法块全部入库

4. **MD5 去重**：
   - 计算清洗后全文的 MD5 哈希值
   - 写入 MySQL `knowledge_md5` 表
   - 下次上传相同内容时直接跳过，避免重复入库
   - 文件名去重基于 MySQL UNIQUE 索引保证

#### 5.1.5 图片向量化

除文本外，文档中的图片同样包含重要信息。本系统对图片进行单独的向量化处理，实现**图文联合检索**。

**图片向量化全流程**：

1. **图片提取**：
   - 使用 PyMuPDF 遍历文档每一页的内嵌图片
   - 调用 `extract_image()` 函数读取原始字节流
   - **自动过滤小于 2KB 的图片**，避免提取无语义价值的图标或装饰

2. **图片向量化**：
   - 使用本地 **CLIP ViT-B-32** 模型
   - `batch_size=16` 批量编码图片为 Embedding 向量
   - CLIP 将图片映射到与文本共享的语义空间，实现"以文搜图"

3. **存入图片向量库**：
   - 存储到独立的 ChromaDB Collection（`rag_images`）
   - 文档内容格式：`"[图片]来源:xxx,第N页"`
   - 元数据包含：
     - `source`：源文件名
     - `page_num`：页码
     - 便于检索时溯源

#### 5.1.6 BM25 关键词索引构建

BM25 是信息检索领域经典的词袋排序算法，基于 TF-IDF 思想改进而来。其核心优势在于对关键词的**精确匹配能力**。

**为什么需要 BM25？**
- 当用户查询包含专业术语时，向量语义检索可能因训练语料分布偏差而召回不相关文档
- BM25 通过词频统计直接定位包含关键词的文档
- 弥补了纯语义检索在精确查询场景下的不足

**BM25 索引构建流程**：
1. 每次文本向量入库后，`BM25Store` 自动检测 ChromaDB 文档数量变化
2. 若文档数量不一致，触发索引重建
3. 从 ChromaDB 的底层 Collection 中读取全量文档文本
4. 使用 **jieba** 进行中文分词
5. 构建 BM25 索引存储在内存中
6. 供在线检索时快速调用

### 5.2 在线检索生成流程

在线检索生成部分由 `RagService` 统一编排。当用户通过前端界面发送问题时，服务端会从 Redis 加载对话历史，经过完整的 RAG 链路处理后，将回答通过 SSE 实时推送到前端。

#### 5.2.1 会话初始化与历史加载

当用户在前端发起对话请求后，服务端首先进行会话初始化：

1. **清理残留状态**：
   - 删除 Redis 中上次中断回答时遗留的终止标记
   - 清除部分回答快照
   - 确保新对话不受历史中断影响

2. **创建线程协作机制**：
   - **消息队列**：工作线程与主线程之间传递 LLM 生成的文本片段，实现逐 token 流式输出
   - **取消标志位**：用户主动停止回答时触发，工作线程检测到后立即终止生成

3. **加载历史消息**：
   - 从 Redis 中加载该会话的完整历史消息
   - 与当前问题和系统指令一并组装为 LLM 的输入上下文
   - 使模型理解对话的来龙去脉，给出连贯回答

#### 5.2.2 查询改写

用户在多轮对话中常使用省略、指代等表达方式（如"那个怎么做？""上面的方法呢？"），这些 query 在脱离上下文后语义不完整。

**查询改写模块工作流程**：

1. **定义系统提示词**：指导 LLM 根据对话历史将用户当前问题改写为独立完整的表述
2. **格式化历史消息**：将历史对话转换为纯文本格式
3. **调用 LLM 改写**：使用 `qwen3.7-max` 模型，非流式调用
4. **失败回退**：若改写失败，回退使用原始 query

**改写效果示例**：
- 用户先提问："直通车 ROI 怎么提升"
- 再问："那有什么具体技巧吗"
- 改写后："直通车 ROI 提升有哪些具体技巧"

改写后的 query 既保留了原始语义，又提高了检索准确性。改写后的 query 同时用于后续的文本检索和话题追踪。

#### 5.2.3 混合检索

经过查询改写后，系统进入混合检索阶段——**同时从语义和关键词两个维度并行召回相关文档**。

**语义检索（Dense Retrieval）**：
- 使用 DashScope `text-embedding-v4` 模型将改写后的 query 编码为高维向量
- 在 ChromaDB 文本向量库中执行余弦相似度搜索
- 返回与 query 语义最相似的 **k=6** 篇候选文档
- **优势**：理解语义层面的相似性，例如"如何提升商品销量"能匹配到"增加营收的方法"
- **局限**：可能忽略精确关键词匹配

**关键词检索（BM25）**：
- 使用 jieba 对 query 进行中文分词
- 在预先构建的 BM25 索引上计算词频-逆文档频率得分
- 同样返回 **k=6** 篇候选文档
- **优势**：精确匹配专业术语和实体名称，如"直通车""ROI""618 大促"
- **局限**：无法理解语义相似性

两路检索各取 6 篇候选文档（共 12 篇）送入下一阶段的 RRF 融合。

#### 5.2.4 RRF 融合

语义检索和 BM25 关键词检索各自产出一组排序结果后，需要合并为统一的文档列表。系统采用 **RRF（Reciprocal Rank Fusion，倒数排名融合）**算法完成融合。

**RRF 核心公式**：

```
score(d) = Σ_{r ∈ R} 1 / (k + rank_r(d))
```

其中：
- `k` 为平滑常数（本系统设为 **60**）
- `rank_r(d)` 为文档 d 在第 r 个检索结果列表中的排名（从 1 开始）
- `R` 是所有检索结果列表的集合
- 若文档不在某列表中，该项为 0

**融合机制**：
- 同一篇文档在语义检索和关键词检索中均出现时，其两路排名分数自然累加
- 获得更高的融合总分
- 最终按总分降序输出合并后的文档列表

**RRF 的优势**：
- 语义向量的余弦相似度与 BM25 的词频统计分数量纲迥异，无法直接比较或加权
- RRF 转而采用**排名**这一无量纲的统一指标
- 天然适合融合异构检索结果

#### 5.2.5 精细重排序

RRF 融合后的候选文档虽经初步排序，但基于排名位置的融合本质上仍属"粗排"范畴。为此本系统引入**本地 BGE-Reranker-v2-M3 模型**进行精细重排序。

**重排序工作原理**：

1. **模型初始化**：
   - 使用 `@property` 懒加载方式初始化约 2GB 权重
   - 确保离线运行，无需外部 API 调用

2. **构造文本对**：
   - 对每个候选文档构造 `[query, doc.page_content]` 文本对

3. **CrossEncoder 打分**：
   - 批量传入 `predict()` 方法
   - 利用注意力机制**同时编码 query 与 document** 进行交互式计算
   - 相较双塔模型的独立编码后余弦相似度，能捕捉更细粒度的语义匹配

4. **筛选 Top-3**：
   - 仅保留分数最高的 **Top-3** 文档
   - 舍弃低分项以控制 Prompt 长度、降低 LLM 推理成本
   - 若候选数不足或推理失败，则回退至融合结果的前 k 篇

**三阶段检索策略**：
```
双路召回 12 篇 → RRF 合并排序 → CrossEncoder 精排 Top-3
```

在保障召回覆盖率的同时，将最终送入 LLM 的上下文压缩至最相关的 3 个片段，兼顾答案质量与 API 成本优化。

#### 5.2.6 图片检索

系统在文本检索之外同步执行图片检索，采用**"语义匹配 + 页码精确匹配"**的双路径策略。

**路径一：CLIP 语义匹配**：
- 使用 CLIP ViT-B-32 模型将 query 文本编码
- 映射至图片向量语义空间
- 在图片 Chroma Collection 中执行向量相似度搜索
- 通过设置相似度阈值过滤低相关结果
- **目标**：响应用户直接询问图片内容的诉求

**路径二：页码精确匹配**：
- 利用已召回文本 chunk 的元数据提取来源页码信息
- 在图片库中精确过滤对应页面下的所有关联图片
- **目标**：确保检索到的文本段落旁若有配套插图亦能被同步捕获

**结果合并**：
- 两类结果以图片描述文本为键去重合并
- 注入 Prompt 实现图文联合增强
- 兼顾语义相关与上下文配套双重场景

#### 5.2.7 分层记忆注入

在多轮对话场景中，用户的每个问题往往承载着前序对话的语境与潜在意图。系统通过分层记忆机制，使 LLM 回答兼顾对话连续性与用户个性化偏好。

**短期记忆（会话摘要）**：

通过**可配置的工作记忆窗口**与**摘要压缩机制**协同运作：

1. **窗口内消息保留**：
   - 最新 6 条消息通过 `MessagesPlaceholder("history")` 保留原文
   - 直接注入 Prompt，支撑当前对话的即时语境

2. **超窗口消息摘要**：
   - 当历史消息总数超过 6 条时，触发摘要压缩
   - 摘要以 `<conversation_id>:summary` 为 Redis 键进行缓存
   - 仅在新消息数超过上次摘要阈值时才调用 `qwen3.7-max` 重新生成
   - 实现增量更新，避免重复调用

3. **摘要生成提示词要求**：
   - 简洁明了，重点保留用户关注的话题
   - 保留重要数据指标、关键决策
   - 保留提及的实体与术语
   - 新摘要基于既有摘要与新消息内容合并生成
   - 保障信息在长对话中的连续性

4. **摘要注入格式**：
   - 以 `"[对话历史摘要]{summary}"` 格式拼接到检索上下文之前
   - 为 LLM 提供跨轮次的高密度对话历史参考

**长期记忆（用户兴趣画像）**：

通过**话题偏好追踪**构建用户画像，实现跨会话的个性化知识沉淀：

1. **话题分类**：
   - 每次用户提问时，调用 `qwen-flash` 模型（非流式，temperature=0.0）
   - 将 query 归类至预定义的 **20 个电商运营主题**
   - 主题包括：引流推广、付费推广、转化成交、店铺运营、商品管理、营销推广、客户服务、数据分析、物流管理、供应链、内容营销、直播电商、社交电商、搜索优化（SEO）、活动策划、品牌建设、用户增长、私域运营、跨境电商、视觉设计、竞品分析、行业趋势

2. **频率统计**：
   - 命中主题后在 Redis Hash 中执行频率计数
   - 同步在 session-level Hash 中记录
   - 支持会话删除时的递减回退

3. **画像注入**：
   - 取频率最高的前 **5 个话题**
   - 以 `"[用户关注话题]"` 格式注入 Prompt
   - 引导 LLM 在回答时侧重用户持续关注的维度
   - 使响应更具针对性与连续性

**附件内容注入**：

若用户在对话中上传了文件：
- 附件内容按知识库文档的处理逻辑进行预处理
- 与知识库检索结果和上下文信息拼接
- 送入模型，让聊天模型更具针对性地回答问题

#### 5.2.8 Prompt 封装

所有上下文信息准备完毕后，系统进入最终的 Prompt 封装阶段。

**Prompt 模板结构**：

```
┌─────────────────────────────────────────┐
│         System 消息（系统提示词）          │
│  • 角色定位：电商运营智能助手             │
│  • 回答风格：简洁、专业、直击要点         │
│  • 知识边界：严格基于知识库资料回答       │
│  • 抑制幻觉：不得臆造不存在的信息         │
└─────────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────┐
│          User 消息（用户输入）             │
│  • 检索到的文档片段（Top-3）              │
│  • 对话历史摘要（短期记忆）               │
│  • 用户兴趣画像（长期记忆）               │
│  • 相关图片信息                          │
│  • 附件内容（如有）                      │
│  • 用户当前问题                          │
└─────────────────────────────────────────┘
```

**System 消息的作用**：
- 设定全局行为指令的特殊角色消息
- 在每次对话开始时发送给 LLM
- 约束模型的回答风格、角色定位、知识边界和输出格式

经过 Prompt 封装后，模型在回答用户问题时：
- 言简意赅，直击用户要点
- 能在一定程度上抑制幻觉问题
- 严格按照知识库资料、上下文信息和附件信息进行回答

#### 5.2.9 LLM 流式生成

Prompt 组装完成后，系统调用 **Qwen3.7-Max** 模型进行流式生成：

1. **流式调用**：
   - 使用 LangChain 的 `stream()` 方法
   - 逐 token 生成回答

2. **实时推送**：
   - 通过消息队列将生成的文本片段传递给主线程
   - 主线程通过 SSE（Server-Sent Events）实时推送到前端

3. **中断处理**：
   - 工作线程持续检测取消标志位
   - 若用户点击停止按钮，立即终止生成
   - 已生成部分保存为快照

#### 5.2.10 消息持久化与会话管理

生成完成后，系统自动进行消息持久化和会话管理：

**消息持久化**：
- 将本轮用户提问与 AI 回答追加写入 Redis 对话历史记录
- 保存会话标题（取用户首次提问截取）和时间戳
- 维护两个会话列表：
  - 用户维度的会话列表
  - 全局会话列表

**中断场景处理**：
- 用户主动中断生成时，系统将当前对话历史、用户问题、已生成的部分回答打包为快照
- 存入 Redis，键为 `<conversation_id>:interrupted`
- 后续加载对话历史时优先返回该快照
- 确保用户刷新浏览器或切换会话后，已生成的部分内容不会丢失

#### 5.2.11 前端 SSE 与渲染

本系统前端基于 **Vue 3** 框架构建：

1. **流式接收**：
   - 通过 `fetch` 结合 `ReadableStream` 流式读取 SSE 事件
   - 逐块拼接 AI 回答文本

2. **Markdown 渲染**：
   - `marked.js` 实时将 Markdown 格式（标题、表格、代码块等）渲染为 HTML
   - 确保用户阅读体验清晰友好

3. **会话切换**：
   - 切换会话时，先将当前未完成的消息缓存至内存
   - 调用停止接口持久化已生成的部分回答
   - 从缓存或后端加载目标会话的历史记录
   - 避免内容丢失

4. **自动滚动**：
   - 每次接收到新内容块，页面自动滚动至底部
   - 确保用户始终能看到最新输出

## 6. 核心模块详解

### 6.1 RAG Chain（rag.py）

RAG 链是系统的核心调度模块，负责串联整个问答流程：

```python
# 核心流程伪代码
def rag_chain(user_query, conversation_id, user_id):
    # 1. 查询改写
    rewritten_query = query_rewrite(user_query, chat_history)
    
    # 2. 语义检索
    semantic_results = vector_store.search(rewritten_query, top_k=6)
    
    # 3. BM25 检索
    bm25_results = bm25_store.search(rewritten_query, top_k=6)
    
    # 4. RRF 融合
    fused_results = rrf_fusion(semantic_results, bm25_results, k=60)
    
    # 5. 重排序
    reranked_results = reranker.rerank(rewritten_query, fused_results, top_k=3)
    
    # 6. 图片检索
    images = image_retrieval(rewritten_query, reranked_results)
    
    # 7. 记忆注入
    memory_context = memory_manager.get_context(user_id, conversation_id)
    
    # 8. 构建 Prompt 并生成
    answer = llm.stream_generate(prompt, context, memory_context)
    
    return answer
```

### 6.2 知识库引擎（knowledge_base.py）

负责整个文档处理管线：

- **文档解析器**：针对每种格式实现专用解析逻辑
- **数据清洗器**：基于规则的文本预处理
- **分块器**：多策略分块 + SemanticChunker
- **嵌入器**：调用 DashScope API 批量生成向量
- **存储器**：写入 ChromaDB + 元数据管理

### 6.3 向量存储（vector_stores.py）

对 ChromaDB 的封装，提供：
- 文本语义搜索接口
- 图片语义搜索接口
- 文档数量统计
- 批量数据写入

### 6.4 BM25 检索（bm25_store.py）

基于 rank-bm25 库实现：
- 使用 jieba 进行中文分词
- 从 ChromaDB 加载所有文档构建倒排索引
- 自动检测文档数量变化并重建索引
- 返回 BM25 分数排序的检索结果

### 6.5 记忆管理（memory_manager.py）

双层记忆架构：

## 11. RAG 评估体系

### 11.1 评估框架概述

本系统采用 **RAGAS（Retrieval Augmented Generation Assessment）**评估体系对 RAG 系统的检索生成质量进行全面评估。RAGAS 是一套专为 RAG 场景设计的开源评估框架，通过四个核心指标从检索与生成两个维度构建系统评价的立体画像。

### 11.2 四大核心评估指标

#### 11.2.1 Faithfulness（忠实度）

**定义**：衡量模型回答是否忠实于检索到的上下文，检测是否存在偏离资料依据的幻觉现象。

**评估方法**：
1. 使用 `qwen-max` 将生成的回答拆解为一组独立的原子级声明
2. 对每条声明，由 `qwen-max` 判断它是否能从检索到的上下文中直接推断出来
3. 计算可支撑声明的比例

**计算公式**：

```
Faithfulness = (可从上下文推断的声明数) / (总声明数)
```

**分数解读**：
- 分数高：模型回答基于事实内容，忠实度高
- 分数低：模型出现幻觉，臆造了上下文中不存在的信息

#### 11.2.2 Answer Relevancy（答案相关性）

**定义**：评估模型回答的内容与用户问题的相关程度，确保模型不会答非所问。

**评估方法**：
1. 让 `qwen-max` 根据生成的回答，反向生成若干个"这个回答可以回应的问题"
2. 将原始用户问题与这些反向生成的问题分别计算 Embedding 余弦相似度
3. 取平均值作为最终的回答相关性得分

**计算公式**：

```
Answer Relevancy = Average(Cosine_Similarity(原始问题, 反向生成问题_i))
```

**分数解读**：
- 分数高：模型回答切题，直接回应用户问题
- 分数低：模型回答跑题，答非所问

#### 11.2.3 Context Precision（上下文精度）

**定义**：评估 RAG 检索到的文档片段中真正有助于模型回答问题的比例，反映检索结果的精确性与信噪比。

**评估方法**：
1. 针对测试集中的问题所检索到的每篇文档，由 `qwen-max` 判断它是否与问题相关
2. 按照检索排名计算 precision@k（本系统 k=3）
3. 保证排名权重递减——相关文档排在越前面，得分越高

**计算公式**：

```
Context Precision = Σ (Precision@k × Relevance(k)) / Σ Relevance(k)
```

其中 `Relevance(k)` 为第 k 个文档的相关性标签（0 或 1）。

**分数解读**：
- 分数高：有用的文档被排在前面，检索优先级质量高
- 分数低：大量无关文档混入检索结果，信噪比差

#### 11.2.4 Context Recall（上下文召回率）

**定义**：衡量模型所给出回答中的关键信息有多少被 RAG 检索的上下文所覆盖，评估检索的全面性。

**评估方法**：
1. 以聊天模型 `qwen3.7-max` 给出的参考答案为基准
2. 用法官模型 `qwen-max` 从中提取所有关键信息点
3. 让模型逐一判断每个信息点是否能从检索上下文中找到依据
4. 计算 recall@k（本系统 k=3）

**计算公式**：

```
Context Recall = (被检索上下文覆盖的关键信息点数) / (参考答案中的总关键信息点数)
```

**分数解读**：
- 分数高：检索覆盖全面，没有遗漏关键信息
- 分数低：检索结果不完整，遗漏了回答所需的重要依据

### 11.3 评估体系的核心价值

采用 RAGAS 评估体系的核心目的，在于为 RAG 系统的**迭代优化**以及**质量评估**提供客观的量化基准。

**解决的核心困境**：
- 修改了分块策略、调整了检索参数或重写了 Prompt 模板后，效果到底是变好了还是变差了？
- 若仅凭个例观察或主观感受，不仅效率低下，更难以捕捉边界情况下的性能退步

**RAGAS 的优势**：
1. **快速实验闭环**：
   - 每当检索策略、分块参数或 Prompt 模板发生变更时，重新运行评估脚本
   - 获得四维指标的精确变化趋势
   - 实现"调整 → 评估 → 对比"的快速实验闭环

2. **零标注成本**：
   - 利用 **LLM-as-a-Judge** 技术，LLM 自身对检索上下文与生成答案的关系进行自动评分
   - 无需人工标注，排除主观偏差
   - 保证评估效率

3. **持续回归评估**：
   - 可在持续部署过程中，随每个版本迭代自动执行回归评估
   - 确保任何改动不会在无意中破坏已有能力
   - 为系统长期稳健演进提供保障

### 11.4 测试集生成

在执行 RAGAS 评估前，需要生成高质量的测试数据。本系统的测试集生成流程如下：

**生成流程**：

1. **文档采样**：
   - 从 ChromaDB 中随机采样 **50 个文档块**
   - 确保测试覆盖知识库的多样性

2. **问答对生成**：
   - 调用 `qwen-flash` 模型为每个块自动生成 **2 组"问题-参考答案"对**
   - 设置 `temperature=0.8` 以增强生成问题的多样性
   - 共生成 100 条测试用例

3. **难度标注**：
   - 每条用例附带 `easy`、`medium`、`hard` 三个难度等级
   - 便于后续按难度维度进行分层评估分析

4. **持久化存储**：
   - 生成的测试集保存为本地 `testset.json` 文件
   - 同时写入 Redis 数据库（db 1）
   - 供评估脚本按需灵活加载

**测试集示例**：

```json
{
  "id": "test_001",
  "question": "淘宝直通车的 ROI 如何计算？",
  "reference_answer": "ROI = 直通车带来的销售额 / 直通车花费，例如花费 1000 元，带来 3000 元销售额，则 ROI = 3。",
  "difficulty": "easy"
}
```

### 11.5 评估执行流程

**完整评估流程**：

1. **加载测试集**：
   - 从 `testset.json` 或 Redis 加载所有测试问题

2. **运行 RAG 链路**：
   - 逐条加载测试问题
   - 调用与生产环境完全一致的 RAG 检索链路获取上下文
   - 由 `qwen3.7-max` 模型生成回答

3. **LLM-as-a-Judge 评分**：
   - 使用 `qwen-max` 作为法官模型
   - 对 RAG 评估的四个维度进行量化打分
   - 基于 RAGAS 框架的评分逻辑

4. **结果汇总**：
   - 计算四个维度的平均得分
   - 按难度等级分层统计
   - 生成评估报告并保存为 `ragas_results.json`

### 11.6 评估结果分析

#### 11.6.1 整体评估结果

**表 6：RAG 整体评估结果**

| 评估指标 | 得分 | 分析 |
|----------|------|------|
| **Answer Relevancy（答案相关性）** | 0.926 | 系统对用户问题的理解与回应对焦精准，极少出现答非所问 |
| **Context Recall（上下文召回率）** | 0.980 | 检索模块基本没有遗漏回答所需的关键信息，召回覆盖率极强 |
| **Context Precision（上下文精度）** | 0.904 | 检索结果信噪比良好，仅有不到 10% 的冗余或无关片段 |
| **Faithfulness（忠实度）** | 0.786 | 相对较低，约 21% 的回答内容未严格忠于检索上下文，存在一定幻觉倾向 |

**整体分析**：

从结果上看，本系统的 RAG 检索和生成结果表现较为稳健：

- **Answer Relevancy（0.926）**：回答相关性优异，说明查询改写和检索策略有效
- **Context Recall（0.980）**：召回率极高，混合检索策略（语义 + BM25）覆盖全面
- **Context Precision（0.904）**：精确度良好，RRF 融合 + BGE 重排序有效提升排序质量

**需要优化的方向**：

- **Faithfulness（0.786）**：是四项指标中的最低值，表明模型在生成时有约 21% 的回答内容未能严格忠于检索上下文，存在一定程度的幻觉或过度推断倾向

**可能原因**：
1. Prompt 中对"基于资料回答"的约束不够强
2. 模型在整合多源信息时产生了非资料支撑的引申
3. 检索上下文包含部分冗余信息，干扰了模型判断

**优化方向**：
1. 更严格的 Prompt 约束，明确要求"仅基于提供的资料回答，不得添加额外信息"
2. 进一步优化重排序模型的阈值，过滤低相关文档
3. 在 Prompt 中添加"若资料不足以回答，明确告知用户"的指令

**Hard 档表现**：
- **Context Recall = 0.893**：骤降，说明高难度问题中有超过 10% 的关键信息未被检索覆盖
- **可能原因**：问题涉及跨段落多跳推理，单一检索策略难以捕捉全部所需信息
- **Context Precision = 0.821**：为最低水平，随着问题复杂度提升，检索结果信噪比变差
- **Faithfulness = 0.835**：反而回升，这并非意味着生成更可靠，而可能是"保守策略"——当检索资料不完整时，模型倾向于只基于有限的资料作答，反而减少了幻觉空间，但同时可能牺牲了回答的完整性

**优化建议**：

针对 Hard 档问题：
1. **引入多跳检索**：对于复杂问题，进行多轮迭代检索，逐步补充信息
2. **增加检索候选数**：将初始召回从 6 篇提升至 8-10 篇
3. **优化查询改写**：针对复杂问题，拆解为多个子问题分别检索
4. **更严格的上下文筛选**：提高重排序阈值，优先保证精度

针对 Medium 档 Faithfulness 问题：
1. **强化 Prompt 约束**：明确要求"严格基于提供的资料回答"
2. **减少冗余上下文**：进一步优化重排序，过滤低相关片段
3. **添加引用机制**：要求模型在回答时标注信息来源，增强可追溯性

### 11.7 评估体系的持续应用

**应用场景**：

1. **版本迭代验证**：
   - 每次修改分块策略、检索参数、Prompt 模板后运行评估
   - 对比前后版本的四维指标变化
   - 确保优化真正有效

2. **A/B 测试**：
   - 对比不同技术方案（如不同嵌入模型、不同重排序模型）的效果
   - 基于量化指标做出技术选型决策

3. **持续监控**：
   - 定期运行评估，监控系统性能是否退化
   - 及时发现并修复问题

4. **边界能力探测**：
   - 通过分难度分析，了解系统在不同复杂度问题下的能力边界
   - 针对性地优化短板

### A. 关键算法说明

#### RRF（Reciprocal Rank Fusion）算法

```
对于文档 d，其 RRF 分数为：
score(d) = Σ_{r ∈ R} 1 / (k + rank_r(d))

其中：
- R 是所有检索结果列表的集合
- rank_r(d) 是文档 d 在列表 r 中的排名（从1开始）
- k 是平滑常数（本项目取60）
- 若文档不在某列表中，该项为0
```

#### BM25 评分公式

```
score(D, Q) = Σ_{i=1}^{n} IDF(q_i) · (f(q_i, D) · (k1 + 1)) / (f(q_i, D) + k1 · (1 - b + b · |D|/avgdl))

其中：
- f(q_i, D) 为词项 q_i 在文档 D 中的词频
- |D| 为文档长度
- avgdl 为平均文档长度
- k1, b 为调参参数（通常 k1=1.5, b=0.75）
```

#### RAGAS 评分公式

**Faithfulness（忠实度）**：
```
Faithfulness = |可从上下文推断的声明集合| / |所有声明集合|
```

**Answer Relevancy（答案相关性）**：
```
Answer Relevancy = (1/n) · Σ_{i=1}^{n} cos_sim(原始问题, 反向生成问题_i)
```

**Context Precision（上下文精度）**：
```
Precision@k = Σ_{i=1}^{k} (相关文档数_i / i) · relevance_i / Σ_{i=1}^{k} relevance_i
```

**Context Recall（上下文召回率）**：
```
Recall@k = |被上下文覆盖的关键信息点| / |参考答案中的所有关键信息点|
```

### B. 数据清洗规则详解

1. **页码移除**：匹配独立数字行（如 "- 42 -"、"第42页"）
2. **页眉页脚移除**：检测重复出现的短行模式
3. **目录检测**：滑动窗口（10行），若3+行匹配 "标题...页码" 模式且连续5+行命中则移除整块
4. **版权页检测**：包含 ISBN/版权/出版社等关键词的段落及前后2行
5. **断行合并**：非句末标点（。！？；…）结尾的行与下行合并
6. **空白归一化**：连续空行压缩为1行，行内多空格压缩

### E. 常见问题排查

**问题 1：ChromaDB 初始化失败**
- 检查 `chroma_db/` 目录权限
- 删除损坏的数据库文件重新初始化

**问题 2：OCR 识别失败**
- 检查 PaddleOCR 模型文件是否完整
- 确认系统内存充足（建议 8GB+）

**问题 3：流式响应中断**
- 检查网络连接稳定性
- 查看 DashScope API 调用日志
- 确认 Redis 连接正常

**问题 4：检索结果质量差**
- 检查 BM25 索引是否已构建
- 重新运行 `download_model.py` 确保重排序模型完整
- 调整检索参数（候选数、相似度阈值）

**问题 5：内存占用过高**
- 减小批量处理的 batch_size
- 定期清理 Redis 过期数据
- 考虑增加系统内存或使用更小的模型
